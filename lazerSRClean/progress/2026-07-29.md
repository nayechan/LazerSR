## 세부패턴 10개 추가 (5 → 15개, 빈 대분류 소멸)

전부 사전 분석 → 사용자 확인 → 구현 → 20,000마디 검증 순으로 진행. 검증은 임시 콘솔 프로젝트를 스크래치패드에 만들어 규칙 위반 수를 세고 확인 후 삭제하는 방식.

### 코드잭 / 미니잭

- `ChordJack34Generator` — 24코드잭의 2동치를 3동치로. 3동치는 "어느 컬럼을 뺄까"가 유일한 자유 변수라 컬럼 균등이 **제외 컬럼 멀티셋 셔플**로 곧장 풀린다. 24코드잭의 상보 쌍 가중 추첨 70줄이 통째로 사라짐 (`90 / 2`)
- `ChordJack23Generator` — 3동치·2동치 교대. **4연타 금지**를 연속 4이벤트 창으로 풀면 `B_{k-1} ∩ B_k ⊆ {a_k}` 하나로 압축됨(마디 경계 lookahead를 피하려 보수적으로 적용). 3연타 금지판은 2동치가 완전히 강제되고 변형이 768까지 떨어져 폐기 (`110 / 2`)
- `MiniJack13Generator` — 3동치 + 따닥 단노트. 4연타 금지가 `s_{k+1} ≠ s_k` 하나로 압축됨. 3연타 금지판은 `s_k = a_{k+1}` 강제라 사실상 잭이 아니었음 (`120 / 5`)
- `MiniJack12Generator` — 2동치 + 따닥 단노트. `s` 균등이 인접 중복 금지를 자동으로 유도(`P_k ∋ s_k`, `P_k ∌ s_{k-1}`이라 `s_k = s_{k-1}`이 모순) (`130 / 5`)
- `MiniJack22Generator` — 2동치를 짝으로 두 번씩. 4연타 허용 / 6연타 금지가 `P_{k-1} ∩ P_k ∩ P_{k+1} = ∅` (`120 / 5`)
- 네 패턴이 **"제약 걸린 균형 수열 두 개"** 라는 같은 골격으로 수렴 → 공용 `PatternPicker`(비트 유틸 + 할당량 가중 추첨) 신설. 기존 생성기는 각자 닫힌 형태로 풀려 건드리지 않음
- 전부 **할당량 가중 그리디 + 마디 재시도**. 20,000마디에서 균등 폴백이 한 번도 발동하지 않음 — 23코드잭에서 `a_k`를 직전 2동치 안에서 우선 고르게 한 것이 후보를 1개→3개로 유지해준 덕

### 스트림 / 핸드스트림 / 테크

- `JumpStreamGenerator` — 짝수 슬롯 동치·홀수 슬롯 단노트. **상보 배제는 데드락 때문에 필수**(단노트 자리가 사라짐) (`80 / 5`)
- `DenseHandStreamGenerator` — 싱글핸스의 자유 슬롯을 2동치로. 양쪽 이웃 배제 규칙 때문에 **추첨이 아예 사라지고** 마디가 `x₀…x₈` 수열로 완전 결정 (`80 / 5`)
- `ContinuousHandStreamGenerator` — 6반복(3동치+1동치 ×6) + 2휴식, **주기 16슬롯 = 마디의 정확히 절반**. 3동치·1동치 비겹침 조건이 6반복을 컬럼 하나로 확정시킴. 축 컬럼을 봉지에서 뽑아 2마디마다 네 컬럼 균등 (`80 / 5`, 마디당 60노트로 최고 밀도)
- `RollTechGenerator` — 4슬롯 그룹의 뒤 두 슬롯이 항상 따닥. **드르륵이 아니라 싱글덤프를 계승** (`100 / 5`)
- `AxisJackGenerator` — 한 컬럼 16연타 + 4이벤트마다 동치. 손 교대 봉지로 4마디마다 네 컬럼 균등 (`100 / 5`)
- 대분류 `짤연` → **`테크`** 로 개명 (id `shortburst` → `tech`)

### 분석에서 잡아 설계를 바꾼 것

- **드르륵테크의 롤 계승이 붕괴함을 증명.** 그룹을 3연속 롤로 두면 따닥 컬럼이 앞 두 슬롯을 완전히 결정하고, 전이표에 **흡수 상태 2개**가 생겨 몇 그룹 안에 `4,3,2,2` 반복으로 굳는다(컬럼 균등 불가). 싱글덤프 계승으로 바꾸니 금지 전이가 0개가 되고 **전체 컬럼 균등이 구조적으로 따라옴**
- **연속핸드스트림 규칙 5의 산술 충돌** — 16연타 = 정확히 1마디라 "2마디에 각 컬럼 1번"은 성립 불가(4마디 필요). 사용자 판단으로 "축 2회, 항상 다른 손"으로 완화
- **축연타도 같은 충돌** — 노트 균등(컬럼당 22)을 지키려면 4마디 창에 네 컬럼이 모두 축이어야 함을 계산으로 보이고 손 교대 봉지 도입

### 점프스트림 실기 피드백 — 긴 한손트릴

**원인 진단**: 상보(데드락 방지)와 동일 반복(잭 방지)을 둘 다 배제하면 남는 4가지가 전부 직전 동치와 정확히 한 컬럼을 공유해 **단노트의 자유도가 0**이 된다. 공유 컬럼은 매 슬롯 눌리므로 강제된 단노트가 같은 손이면 트릴이 되고(확률 1/2), 같은 컬럼을 계속 무는 동치 2가지가 번갈아 나오는 **자기유지 2-사이클**에 갇히면 길어진다.

1차 대응으로 동일 반복 배제를 제거(단노트 자유도 부활) → 사용자가 극단에 강한 제약을 요구 → **트릴 5노트 금지 + 동일 동치 4연속 금지**로 재구현.

- 첫 구현은 "같은 손 트릴 스텝 2연속 금지"라는 국소 규칙이었는데 **검증에서 5노트 트릴이 마디당 0.38회 남음**. 트릴 스텝 하나(3노트)가 앞뒤 단노트에 의해 양옆으로 늘어나며, 그 확장은 이웃 스텝이 트릴이 아니어도 발생함을 확인
- **손별 교대 런 길이를 상태로 들고 슬롯마다 갱신**하는 방식으로 교체, (다음 동치, 단노트) 조합 단위로 검사. 재검증에서 5노트 트릴 0회
- 데드락 없음의 근거: **한손 동치를 놓으면 한 손 2노트·다른 손 0노트가 되어 양손 런이 동시에 끊긴다** — 항상 열려 있는 탈출구

## 음악 시스템 (박자 고정 BGM)

### 사전 조사 (osu! 원본 직접 확인)

- 게임플레이 시계의 소스 트랙 교체는 **기술적으로 가능**하다 — `MasterGameplayClockContainer.StopUsingBeatmapClock()`이 public이고 절차를 그대로 보여주며(`ChangeSource` → 조정 재적용), `Player.CreateGameplayClockContainer`가 `protected virtual`이라 서브클래스로 노출 가능. **하지만 다곡 재생에는 부적합** — 그 경로에서는 곡의 재생 위치가 곧 게임플레이 시각이라 83분 세션과 2~5분 곡이 어긋나고, 되감으면 주입 노트가 전부 강제 미스가 된다
- → **독립 채널 재생**으로 결정. osu! 본체 `BackgroundMusicManager`(랭크드 플레이)가 `DrawableTrack` + `audio.Tracks.Get`으로 같은 일을 하는 프로덕션 선례
- 배속은 `AddAdjustment(Tempo|Frequency, bindable)` 값 변경으로 즉시 반영됨(`ModTimeRamp`가 매 프레임 갱신하는 것이 근거). `Tempo` = 피치 유지 채택

### 분석에서 잡은 것

- **절반 bpm으로 스냅하면 마디 정렬이 깨진다.** 맵퍼들이 프리뷰를 원본 마디 시작에 정확히 찍어놨는데(4곡 중 3곡), bpm을 절반으로 잡으면 마디 길이가 2배가 되어 그 지점이 마디 한가운데가 된다 → **원본 bpm 마디 그리드 기준으로 스냅**하기로 확정. 훈련 마디가 소비하는 원본 오디오는 `240000/펄스bpm`이라 원본 마디의 정수배가 되어 세트 내내 정렬이 유지됨
- **고정 저장 bpm은 배속이 0.47~2.33까지 튄다.** osu!는 자신이 쓰는 범위를 `[0.5, 2.0]`으로 두고 있음(하프타임 하한, `UserPlaybackRate` 상한) → **한계를 벗어날 때만 옥타브를 옮기는** 방식 채택. 순수 옥타브 정규화는 배속을 1.0 근처로 유지하는 대신 사용자가 정한 곡별 펄스 판단을 덮어쓰고 탐색 도중 체감 펄스가 뒤집힘
- **정확한 시각에 트랙을 시작하는 것은 불가능**(BASS 시작 지연) → **인과를 뒤집어** 트랙을 먼저 돌리고 실제 재생 위치를 읽어 "다음 다운비트가 오는 게임플레이 시각"을 세트 시작으로 삼는다. 세트마다 재동기하므로 드리프트가 누적될 구간이 없어짐
- 세트가 소비하는 원본 오디오는 `480000/펄스bpm` = 2.8~5.6초로 **패턴 bpm과 무관**. 프리뷰 이후 남은 길이가 최소 50초라 곡 소진은 발생하지 않음

## 조사

## 구현

- `Drawables\ManiaJudgementLineOverlay.cs` 생성 — 컬럼 1개분 판정 기준선. 정지선 1개(Y=0) + 스크롤선 N개
- `Patches\ManiaJudgementLinePatch.cs` 생성 — `Player.LoadComplete` Postfix. `ReplayPlayer`/`SpectatorPlayer`일 때만, mania일 때만 동작. `drawableRuleset.Objects`에서 컬럼별 판정 시각 수집(단노트 `StartTime`, 롱노트 `StartTime`+`EndTime`) 후 각 컬럼에 오버레이 부착

**구현하며 정한 것**:
- **`DrawableHitObject` + `ScrollingHitObjectContainer` 방식을 쓰지 않았다** — 판정되지 않는 DHO는 `updateState`에서 `LifetimeEnd`가 `double.MaxValue`로 남아(`DrawableHitObject.cs:487` 조건이 `state != Idle || HitWindows == null`) 컬링이 안 된다. 대신 정렬된 시각 배열 + 이분 탐색 + Box 풀로 직접 윈도잉
- **위치 계산은 전부 `ScrollingHitObjectContainer.PositionAtTime(time)`에 위임** — osu!가 노트를 배치하는 것과 같은 경로라 SV·스크롤속도·재생배속이 자동 반영. 자체 px/ms 환산 없음
- **`HIT_TARGET_POSITION` 하드코딩 안 함** — `HitObjectArea`가 이미 히트포지션 패딩이 적용된 좌표계라 Y=0이 곧 진짜 판정선. 스킨이 `HitPosition`을 바꿔도 자동 추종
- **부착 위치는 `column.HitObjectArea`**(`UnderlayElements` 아님) — 노트보다 앞에 그려야 선이 가려지지 않는다
- 이분 탐색을 매 프레임 새로 하므로 되감기/시크에 상태 없이 대응

**알려진 사실 (버그 아님)**: 다운스크롤에서 `DrawableManiaHitObject`는 `Origin = BottomCentre`라 **단노트/LN헤드는 스프라이트 아랫변**이 판정 지점이고, `DrawableHoldNoteTail`은 방향 무관 `Origin = TopCentre` 고정이라 **LN 테일은 스프라이트 윗변**이 판정 지점이다. 선이 노트 중앙이 아니라 모서리에, 그것도 헤드/테일이 서로 반대 모서리에 붙는 게 정상이다.

## 판정 시뮬레이션 — 전면 실패 수정

**증상**: 맵 길이/복잡도와 무관하게 사각형이 전부 회색, 숫자 없음. 시뮬레이션이 아예 안 돌았다.

**원인**: `SetReplayScore()`를 룰셋이 로드되기 **전에** 호출했다. 이 메서드는 내부에서 `frameStabilityContainer.ReplayInputHandler`를 세우는데(`DrawableRuleset.cs:315`) 그 컨테이너는 BDL `load()`에서 생성된다(`:177`). 트리에 붙기 전(= BDL 실행 전)이라 null → `NullReferenceException`이 BDL 밖으로 나가 **시뮬레이션 드로어블 자체가 로드 실패** → `Ready`가 영원히 false.

osu! 본체가 `PrepareReplay()`를 `Player.load()`가 아니라 `Player.LoadComplete()`에서 부르는 이유가 정확히 이것이었다.

**수정**:
- `LoadComponent(drawableRuleset)`로 먼저 로드한 뒤 `SetReplayScore` 호출
- BDL 전체를 try/catch로 감싸고, 실패해도 반드시 `complete()`를 불러 `Ready`를 세운다 — **조용한 영구 대기가 이번 실패의 본질이었다**
- 시각이 600회 연속 안 움직이면 포기하는 stall 가드 추가 (매 프레임 예산을 영원히 태우는 것 방지)
- 완료 시 그림자 룰셋을 `Schedule`로 제거·폐기 — 안 그러면 게임플레이 내내 매 프레임 업데이트되고 메모리도 붙잡는다

## 판정 시뮬레이션 — 긴 맵 조기 종료 버그 + 숫자 가독성

**로그로 드러난 버그**: 짧은 맵(94초)은 497회 만에 정상 완주했지만, **13.5분 맵은 600회에서 stall 가드에 걸려 중단**됐다 (`600 iterations, stalled=600, endTime=809,314`). 809초 중 약 120초분(판정 3,049개 / 누름 15,176개)만 얻고 나머지는 전부 회색.

**원인**: `lastFrameStableTime` 초기값이 `double.NaN`이었다. `Math.Abs(x - NaN)`은 NaN이고 `NaN > 0.01`은 **항상 false**라 정상 진행도 전부 "멈춤"으로 세었다. `stalledIterations`가 리셋 없이 단조 증가해 600에서 강제 종료. 짧은 맵은 497회에 끝나 한도에 닿기 전에 완주해서 증상이 안 보였다.

진행 로그가 `frameStable=NaN`을 계속 찍고 있던 것도 같은 원인 — 로그도 `frameStableTime`이 아니라 `lastFrameStableTime`을 찍고 있었다.

**수정**:
- 초기값 `double.NaN` → `double.NegativeInfinity`, 판정식에 `!double.IsFinite(lastFrameStableTime)` 추가
- 진행 로그가 실제 `frameStableTime`과 `stalled` 카운터를 찍도록 수정
- **처리량 상향**: 로딩 중 예산 25ms → 60ms. 실측 25ms에서 13.5분 맵이 약 24초 걸려 게이트 한도를 넘겼다
- 게이트 타임아웃 15초 → 30초

**실측 (수정 전, 25ms 예산 기준)**: 94초 맵 = 2,297ms / 13.5분 맵 = 3,658ms(중단 시점). 셋업만 각각 144ms / 192ms.

# 버그 수정 3건 + 결과창 판정 산점도 (후속 세션)

## 클래식 정확도 위젯 — 배속에서 값이 어긋나던 버그

**증상**: 정배속은 정상, DT/HT/사용자 배속에서 **그 배율만큼** 정확도가 어긋남.

**원인**: mania 판정창은 배속에 비례해 **함께 늘어난다** (`ManiaHitWindows.SpeedMultiplier`, 주석에 "판정창을 트랙 속도와 무관하게 유지"라고 명시). 반면 `JudgementResult.TimeOffset`은 비트맵 시간 기준이라 배속만큼 커진 값이 그대로 온다. 위젯은 그 커진 오차를 **고정 판정창**(`64/97/127/151-3*OD`)에 대입하고 있었다. osu! 본체도 UR 계산에서 `e.TimeOffset / e.GameplayRate`로 같은 보정을 한다(`HitEventExtensions.cs:44`).

**수정**: `normalisedOffset()` 헬퍼 추가 — `TimeOffset / |GameplayRate|`. `onNewJudgement`/`onJudgementReverted` 양쪽 입구에서 한 번만 정규화해 롱노트 head/tail 평균과 되돌림 대칭성을 그대로 유지. 되감기 중 `GameplayRate`가 음수일 수 있어 절댓값 사용.

**미수정으로 남긴 것**: mania EZ/HR은 OD가 아니라 **판정창 폭에 직접** 1.4배/÷1.4를 건다(`DifficultyMultiplier`). 위젯은 비트맵 원본 OD만 쓰므로 EZ/HR에서는 여전히 어긋난다 — "구클라 방식" 사양의 의도일 수 있어 판단 보류.

## 멀티 로비 난이도 아이콘 툴팁 — sunnySR pill이 stale 값을 보여주던 버그

**원인**: pill이 `SunnyState.CurrentSr`(전역 단일 슬롯)에 묶여 있었다. 이 슬롯은 송 셀렉트와 로딩 화면만 쓰므로 멀티 로비에서는 **직전에 미리보던 맵의 값**이 그대로 남는다.

**수정**: 4.2(`ExpandedPanelMiddleContentPatch`)와 같은 **로컬 bindable + 그 자리 재계산** 방식으로 전환.
- 툴팁이 실제 표시 중인 `displayedContent`에서 `BeatmapInfo`/`Ruleset`/`Mods`를 읽어 계산
- 매번 0으로 리셋 후 이전 계산은 CTS로 취소 — 계산 중/미다운로드는 0
- 큐 항목은 온라인 비트맵(`APIBeatmap`)이라 로컬 사본을 **MD5 우선 → OnlineID 폴백**으로 조회 (osu!가 플레이리스트 항목의 "다운로드됨" 판정에 쓰는 순서와 동일)
- mania가 아니면 pill을 숨긴다
- 모드는 `DeepClone()`해서 넘긴다
- `BeatmapManager`는 툴팁의 `Dependencies`에서 얻되 최초 성공 참조를 static 캐시 (첫 `SetContent` 시점엔 아직 로드 전일 수 있음)

**1차 구현이 실기에서 실패했고 그 원인이 중요**: 호버 중에는 값이 안 뜨고 마우스를 뗀 뒤 페이드아웃 동안에만 값이 올라왔다. osu.Framework의 `TooltipContainer`가 **매 프레임 `SetContent`를 다시 호출**하는데 `DifficultyIcon.TooltipContent`는 접근할 때마다 **새 객체**를 반환하고 그 타입은 `Equals`를 재정의하지 않는다 → 프레임마다 취소·리셋이 반복되어 계산이 끝날 틈이 없었다. **대상 식별 키**(`MD5|OnlineID|룰셋ID|모드+설정값`)를 두고 키가 바뀔 때만 재계산하도록 수정. 모드 설정값을 키에 넣은 것은 rate-adjust처럼 아크로님이 같고 배속만 다른 경우 때문.

## 결과창 판정 산점도 (mania, 신규)

결과창 확장 통계 패널(스페이스바)의 판정 분포도 **바로 아래**에 산점도를 추가. 가로축 시간(첫 노트~마지막 노트), 세로축 판정 오차(위 얼리 / 아래 레이트), 점 하나가 노트 하나.

- 삽입은 `StatisticsPanel.CreateStatisticItems` Postfix. `"Timing Distribution"` 항목을 **이름으로 찾아** 그 뒤에 넣는다(인덱스 하드코딩 회피)
- `requiresHitEvents: true` — 리플레이 미재생 스코어에서는 osu!가 알아서 항목을 빼고 기존 안내 문구로 대체한다. 우리 쪽 처리 없음
- 점 색은 `OsuColour.ForHitResult` 그대로. 바로 위 히스토그램과 같은 색 체계라 범례 없음
- 미스 제외 — `TimeOffset`이 미스 판정창 값으로 클램프되므로 실제 오차가 아니라 상수다(그대로 찍으면 가장자리 직선 하나). `HoldNote` 본체/바디도 `HitWindows`가 Empty라 같은 조건에서 함께 걸러진다
- 세로축은 **OD에서 자동 계산된 미스 판정창 ±로 고정**(실측 최대치 아님). 판정창은 실제 판정된 히트오브젝트의 `HitWindows`에서 읽으므로 EZ/HR 배율까지 자동 반영
- 배속 정규화: 오차와 판정창을 **둘 다** `GameplayRate`로 나눠 실시간 ms 기준. 클래식 정확도 수정과 같은 보정
- 배경에 320/300/200/100/50 판정창 경계선 + 0선. ±16ms(320) 라벨만 생략(0선과 겹침)
- 하단 토글 버튼 3종(**단노트 / 롱헤드 / 롱테일**, 기본 전부 활성). 분류는 `TailNote` → `HeadNote` → `Note` **순서로** 검사한다 — 셋 다 `Note`를 상속하므로 순서가 곧 분류 규칙이다
- 토글 시에는 좌표 재계산 없이 **필터만 다시 건다**
- 버튼은 `OsuClickableContainer` + `Box` + 라벨로 직접 구성. `RoundedButton`은 `TrianglesV2`/`OverlayColourProvider` 의존이 있고 `OsuButton`은 abstract
- 렌더링은 `StrainAreaGraph`의 커스텀 `DrawNode` + 쿼드 배치 계승 — 점이 몇 개든 Drawable은 1개

**설계 조사에서 확정한 것**: `ManiaRuleset.CreateStatisticsForScore`(mania 전용 + 배열 반환이라 더 깔끔해 보임)를 패치하는 것은 **불가능**하다. `Patcher`가 `osu.Game` 로드 직후 `PatchAll`을 돌리는데 그 시점에 룰셋 어셈블리는 미로드라 `Prepare()`가 false → **영구 스킵**(재시도 경로 없음). `osu.Game` 소속인 `StatisticsPanel`을 타겟으로 잡고 `OnlineID != 3` 가드로 mania 한정.

## 산점도 — 노트 많은 맵에서 렉/클라이언트 종료

**증상**: 노트가 많은 맵의 결과창에서 극심한 렉, 때로는 osu! 종료.

**원인**: `CreateQuadBatch<T>(size, maxBuffers)`의 첫 인자는 정점 수가 아니라 **쿼드 수**인데 `points.Length * 4`를 넘기고 있었다(필요량의 4배). `IRenderer.MAX_QUADS = 10922`가 하드 상한이고 초과 시 `VeldridQuadBatch` 생성자가 **`OverflowException`** 을 던진다(프레임워크 IL에서 직접 확인). 즉 **표시 점 2,731개 이상이면 예외**.

진짜 문제는 예외 자체가 아니라 그 뒤였다 — 생성이 실패하면 `batch`가 `null`로 남아 **다음 프레임에 또 던진다.** 드로우 스레드의 무한 예외 루프가 곧 "렉"이고, 이 예외가 밖으로 새면 클라이언트가 죽는다. 토글로 점 수가 한도 아래로 내려가면 증상이 사라지는 것도 이걸로 설명된다.

이 `* 4`는 `StrainAreaGraph`에서 계승한 것이고, osu! 본체의 `BeatmapMetadataWedge.FailRetryDisplay`도 같은 관용구를 쓴다 — **원본이 틀렸는데 데이터가 작아 아무도 안 걸린 케이스**다.

**수정 전 확인**: 프레임워크 IL로 `VeldridVertexBatch.Add`가 버퍼가 차면 `Draw()`로 플러시하고 이어서 담는 것을 확인했다. 배치 크기를 고정해도 **점은 하나도 버려지지 않는다.**

**수정**:
- 배치 크기를 점 개수와 분리해 **고정 2,048 쿼드**로. 생성 인자가 상수라 한도 초과가 구조적으로 불가능하고, 토글마다 GPU 버퍼를 재생성하던 경로도 사라짐(`??=`). 메모리 약 460KB 고정, 드로우 콜은 `ceil(점 수 / 2048)`
- `Draw` 전체를 try/catch로 감싸고 실패 시 `drawFailed`로 **재시도를 중단**. 셰이더는 `finally`에서 언바인드

**남겨둔 것**: `StrainAreaGraph`의 같은 `* 4`(300개 다운샘플이라 도달 불가), 텍스처 미바인딩(검증된 렌더 경로 유지), 매 프레임 전 점 재계산(이번 렉의 원인이 아니었음 — 필요해지면 `BufferedContainer` 캐싱이 다음 카드).
