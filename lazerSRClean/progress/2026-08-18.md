# 2026-08-18

저장 기능(세션 간 유지가 필요한 데이터의 공용 보관소) 설계 방향만 결정. **코드 작업 없음** — sunny 계산 방향 자체를 다른 세션에서 재검토 중이라 구현은 보류.

## 결정 사항

**저장 루트: `%LocalAppData%\LazerSR\`**

- 설치 경로는 관리자 권한이 필요하고 인스톨러 재설치 때 덮이므로 데이터를 두지 않는다.
- Roaming(`%AppData%`)이 아니라 Local인 이유: 계산 캐시는 그 PC의 비트맵 라이브러리에 종속된 데이터이고 용량이 커질 수 있다.
- Hook(osu! 프로세스)과 Launcher 모두 일반 사용자 권한으로 읽고 쓸 수 있다.

**런처 설정은 지금 위치(`%AppData%\LazerSR\settings.json`) 유지.** 작동 중인 코드를 건드리지 않는다. 설정과 캐시는 성격이 다르므로 위치가 갈리는 것이 자연스럽다.

**인스톨러 제거 시 저장 폴더를 지우지 않는다.** 전수조사처럼 시간이 드는 데이터라 업데이트 재설치에서 날아가면 손해가 크다.

**기능별로 폴더/파일 분리** (`sunnysr\`, `training\` …). 통짜 `state.json` 금지 — 기능 독립 원칙 위반이고 한 기능의 손상이 전부를 날린다.

**공용화는 경로 결정 + 폴더 보장 + 원자적 쓰기(임시 파일 → `File.Replace`) + 안전한 읽기(손상 시 빈 상태 반환)까지만.** 범용 key-value 추상화는 만들지 않는다. 스키마·직렬화는 각 기능이 소유한다. 경로 코드는 Hook에 두고 Launcher가 참조(기존 참조 방향과 일치).

## 첫 저장 대상 — sunnySR 캐시 (설계만)

**키 = 비트맵 MD5 + 모드 서명 + 계산기 버전**

- MD5: 로컬 사본 조회에 이미 쓰는 식별자(`architecture.md` §13). `OnlineID`는 언랭크드/로컬 편집본에 없어 키로 못 쓴다.
- 모드 서명: 배속이 값을 바꾸므로 필수. **아크로님만으로는 부족** — rate-adjust처럼 아크로님이 같고 설정값만 다른 경우가 있다(툴팁 재계산 가드와 동일 규칙).
- 계산기 버전: sunny 파이프라인 수정 시 저장값 전부 무효. 다르면 캐시 미스로 취급. 수동 정수로 충분. **이 필드가 없으면 알고리즘 수정 후 값이 안 바뀌는 문제로 시간을 태운다.**

**값**: sunnySR 실수값(+ 같은 계산의 부산물인 dominant skillset 정도). **strain 타임라인은 저장하지 않는다** — 맵당 수천 점이라 용량이 수백 배가 되고 실시간 계산으로 충분하다.

**형식**: 한 줄에 한 항목(JSON Lines 등) 또는 단순 이진 파일 하나 + 시작 시 메모리 딕셔너리로 전량 적재. 10만 맵이어도 5~10MB 수준이라 DB가 필요한 규모가 아니다.

- SQLite 배제 — Hook의 어셈블리 해석을 `DependencyResolver`가 직접 하는 구조라 네이티브 의존성 추가는 배포·해석 경로를 같이 손대야 하는데 얻는 게 없다.
- 맵당 파일 1개 배제(파일 10만 개), 통짜 JSON 배열 배제(항목 하나 추가에 전체 재작성).
- 헤더에 스키마 버전. 모르는 버전이면 조용히 빈 상태로 시작 — 재생성 가능한 캐시라 마이그레이션하지 않는다.

## 운용 규칙

- **`StartupHook.Initialize()`에 파일 I/O를 넣지 않는다** (osu! `Main()`보다 먼저 동기 실행되는 하드 제약). 첫 조회 시 백그라운드 적재.
- 쓰기는 모아서 — 값마다 내려쓰면 전수조사에서 I/O가 폭발한다. 주기적 + 종료 시 flush.
- 파일 접근은 UI 스레드 밖에서.
- **캐시 실패는 절대 기능을 막지 않는다.** 없음/손상/잠김이면 캐시 미스로 떨어지고 평소대로 계산한다. 저장소는 가속 장치이지 정답의 출처가 아니다 — 이 성질 덕에 다중 프로세스 락이 필요 없다(원자적 교체 + 실패 시 미스로 충분).
- 삭제된 맵의 항목은 방치해도 무해(한 줄 수십 바이트). 필요해지면 realm에 있는 MD5만 남기고 재작성.

## 안전

레드라인 전부 통과 — 우리 폴더에만 쓰고 osu! 파일·realm 저장값에 쓰지 않으며 네트워크 호출이 없고 서버 제출값과 무관하다. MD5·메타데이터는 읽기만.

전수조사를 실제로 돌릴 때는 realm을 장시간 붙잡지 않도록 맵 목록을 먼저 스냅샷으로 뽑고 그 위에서 계산할 것 — 저장소가 아니라 전수조사 작업 쪽 사안.

# 무한 트레이닝 손보기 (같은 날 후속 세션)

## 임계 정확도 단순화 + 장기 폐기

- `PatternGroup`에서 `ContinuousThreshold`/`PassThreshold` 제거 — 임계는 패턴별이 아니라 **단기/무한 2종**뿐이고 사용자가 대기 화면에서 직접 정한다. 임계 조회용이던 `PatternCatalog.GroupOf()`도 소비처가 사라져 삭제
- `ShortTermSearch`가 임계 하나를 생성자로 받아 지속상승·휴식상승이 같은 값을 쓴다 (T1/T2 구분 소멸)
- 임계 UI는 텍스트 입력 → **−/+ 스테퍼**(0.1 단위, 기본 96%)로 교체. 입력 박스와 파싱 코드 제거
- **장기 실력찾기 전면 폐기** — `TrainingPhase.LongTerm`, 위젯 제목, `TrainingProfile.GetLongTermBpm()`, 패턴 목록의 "장기 —" 열, 설정 패널 체크박스 전부 삭제
- `PatternListPanel`의 private nested `StepButton`을 `Screens\StepButton.cs`로 분리해 설정 패널과 공유. 게임플레이 HUD에는 `OverlayColourProvider`가 없으므로 `[BackgroundDependencyLoader(true)]` + 폴백 색

## 배경음 — 동봉 4곡 → 사용자 비트맵 참조

- `Music\` 폴더, 매니페스트 로딩, 런처 csproj의 `Music\**` 복사, 인스톨러 `[Files]`의 `Music\*` 전부 삭제
- 신규 `LazerSrStorage.cs` — 저장 루트 `%LocalAppData%\LazerSR\`, 폴더 보장 + 원자적 쓰기(임시 파일 → `File.Move`) + 안전한 읽기. **네임스페이스는 루트에 둔다** — `LazerSR.Hook.Storage`로 두면 osu.Framework의 `Storage` 타입과 이름이 충돌해 같은 어셈블리의 다른 파일이 깨진다
- 신규 `Training\TrainingMusicStore.cs` — `%LocalAppData%\LazerSR\music\songs.json`, 스키마 버전(현재 2), 추가/삭제/활성 토글
- 신규 `Training\BeatmapMusicAnalysis.cs` — 적합성 검사. 오디오 정보 → 타이밍 → **변속**(개수가 아니라 서로 다른 박 길이 수: 같은 bpm을 여러 번 찍은 맵이 흔하다) → 4/4 → 오디오 길이 → **프리뷰 미설정이면 불가**(40% 폴백은 마디와 무관) → **여유 45초** → 오디오 실존
- `MusicTrackInfo` 재정의 — 파일명 대신 `BeatmapMd5`/`AudioFile`/`AudioHash` + `DifficultyName`/`SpareMs`/`Enabled`. **절대 경로를 저장하지 않는다**(osu! 데이터 폴더를 옮기면 전부 깨진다), 재생 직전에 realm으로 재해결
- `MusicLibrary`는 스냅·배속 계산만 남기고 목록은 스토어에서 받는다. `Resolve`/`LoadTrack`/`PruneMissing` 추가 — realm 해결 경로를 재생기·미리듣기·정리·행 배경이 공유
- `TrainingMusicPlayer`가 `Music\` 트랙 스토어 대신 `MusicLibrary.LoadTrack()` 사용. **한 곡이 안 열리면 다른 곡을 집어보고** 전부 실패해야 음악을 끈다(참조 방식이라 맵 삭제로 곡이 사라질 수 있다)

## 곡 등록 UI (선곡 화면 위젯)

- `TrainingStatusWidget`이 **선곡 화면에 배치되면 곡 등록 위젯**이 된다. osu!에 `GlobalSkinnableContainers.SongSelect` 레이어가 있고(`SongSelect.cs:306`) `GetAllAvailableDrawables`는 컨테이너별로 거르지 않아 등록 코드 변경이 필요 없었다. 모드 구분은 **`GameplayState` 캐시 여부**
- 표시는 `사용 가능`/`사용 불가` 2종만. 펄스 bpm은 `−10 − [값] + +10` 두 세트, 절반 추정 기준 180
- **펄스 bpm은 자동 판정 불가** — 등록했던 4곡 중 하나(Pentagramma 170)가 절반이 아니었다. 추정값만 넣고 사용자가 고친다
- 중복은 **오디오 해시**로 막는다(검사는 난이도 단위지만 오디오는 맵셋 공용)

## 대기 화면 곡 목록 (`Screens\SongListPanel.cs` 신규)

- 우측이 3단으로 — 설정(336px) / 곡 목록(남는 높이) / 시작 버튼(70px)
- 행: 체크박스 / ▶ / 난이도 이름 / `37s` / `137bpm`(**펄스 bpm**) / ×
- 행 배경에 비트맵 이미지 — `UpdateableBeatmapBackgroundSprite` + 검정 그라데이션(`DrawableRoomPlaylistItem`과 같은 구성). **바깥 컨테이너에 `FillMode.Fill`을 주면 안 된다** — `RelativeSizeAxes.Both`와 만나면 컨테이너가 정사각형으로 부풀어 이미지 윗부분만 보인다. 크롭 중앙 정렬은 안쪽 스프라이트가 이미 하고 있다
- **곡 구성이 바뀔 때만 행을 재생성**한다(해시 순열 비교). 체크박스 토글로 전 행을 다시 만들면 배경 이미지가 매번 다시 로드된다. ▶/■는 라벨만 교체
- `DrawableTrack`은 로드 전에 `Seek`/`Start`가 먹지 않아 `OnLoadComplete`로 미룬다
- 대기 화면 `OnEntering`에서 `PruneMissing` — 원본 비트맵이 사라진 곡을 자동 제거

## 무한 세션 (1차)

- 신규 `Training\InfiniteSession.cs` — 패턴 **비복원 추첨**(소진 시 봉지 재충전, 위젯용으로 3개 미리 뽑음), 세트 = 패턴 하나 × **40초를 넘지 않는 최대 마디 수**, bpm 고정, **휴식 8초**(마지막 노트가 판정된 시각부터), 배경음은 세트마다 새 곡
- **조기 종료** — 세트 누적 정확도가 목표 미만인 상태가 5초 이어지면 새 노트 공급만 끊는다. 이미 나간 노트는 그대로 내려온다
- `TrainingSequencer.StopEmitting()` 추가 — 미주입 마디 폐기 + **실제로 나간 노트 수/끝 시각** 반환 + 다음 세트 시작 기준을 그 끝으로 당김
- `JudgementAggregator.TruncateSet()` 추가 — 세트 완료 조건을 실제로 나간 만큼으로 정정하고 즉시 완료 검사. **없으면 오지 않을 판정을 기다리며 세션이 멎는다**
- 설정 패널에 "무한 세션 실행" 체크박스(단기와 배타) + 무한 전용 목표 정확도. 둘 다 끄면 시작 버튼 비활성
- `InfiniteTrainingPlayer(TrainingPhase mode, double threshold)`로 모드 분기
- 위젯은 무한 휴식 중 **저장/폐기 버튼을 숨기고** 다음 패턴을 예고. sunnySR은 bpm 고정이라 **패턴당 1회만 계산**
