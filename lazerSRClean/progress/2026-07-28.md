## 패턴 생성 시스템 설계 논의

무한 트레이닝을 "패턴 훈련 시스템"으로 확장하는 구상을 자연어로 진행. 전체 흐름은 **단기실력찾기 → 장기실력찾기 → 무한세션** 3단계이고, 평가 패턴은 7종(스트림/점프스트림/핸드스트림/덤프/짤연/미니잭/코드잭) × 세부패턴 3개 = 21개.

- 생성 모델은 매 순간이 아니라 **세트 단위 폐루프** — 세트를 통째로 생성 → 플레이 → 판정 집계 → 다음 세트 파라미터 결정
- 논의로 확정된 것: 기록·판단 단위 = 1마디 / bpm은 노트 간격에만 반영(배속 사용 금지) / 마디에 생성 파라미터 태그를 달아 전환 지연을 집계 문제로 환원 / 단기는 세트 간 공백으로 파이프라인 지연 흡수, 장기는 판단을 k마디 앞당겨 연속성 유지
- **파이프라인 지연은 제거 불가**(노트가 스크롤 시간만큼 미리 존재해야 함)라는 것이 설계의 출발점. 지연을 없애는 대신 최소화 + 귀속 규칙 명확화로 접근
- 정확도 공식 확정: 분모 320, 분자 `[320,300,200,100,50,0]` 산술평균
- 단기탐색 3단계 확정: **지속상승**(무휴식, 매 세트 +1스냅, T1 미달 시 종료) → **휴식상승**(휴식 삽입, 통과 시 +1스냅·미달 시 −1스냅) → **검증**(bpm 고정, 4마디 세트 5회 중 3회, 단조 규칙으로 진동 방지). 임계는 T1 > T2 두 개이며 큰 패턴 단위, 시작 bpm·스냅은 세부패턴 단위
- 장기실력찾기는 무한세션에 흡수될 여지가 있어 **논의 보류**
- bpm은 패턴별 스냅의 정수배(정수)

### 격자 규칙 확정 (모든 패턴 공통 절대규칙)

```
1마디 = 32슬롯(32분음표) × 4컬럼 = 128슬롯
슬롯 = 7500 / bpm ms,  마디 = 240000 / bpm ms
16분음표 = 2슬롯, 8분음표 = 4슬롯
```

논의 중 마디 길이 계산이 어긋난 지점이 있어 정정 — 120bpm 4/4 마디는 2초다. 셋잇단은 정형 패턴 생성에 불필요하다는 판단으로 1/48 → 1/32 격자로 확정(필요해지면 bpm 변환으로 흡수 가능).

### 24코드잭 사양 확정

- 4동치 슬롯 0,4,…,28 / 2동치 슬롯 2,6,…,30 → 마디당 16이벤트·48노트
- 2동치 컬럼 선택은 **마디 내 균형 강제** — 각 컬럼 정확히 4회. 이 조건을 풀면 **상보 쌍끼리 개수가 같다**는 성질만 남고(`n{01}=n{23}`, `n{02}=n{13}`, `n{03}=n{12}`, 합 4), 가능한 배열은 44,730가지
- 같은 손 2동치 허용. 손 부하는 상보 쌍 성질 덕에 자동으로 대칭

### OD/HP 관련 코드 확인 결과 (osu! 소스 직접 확인)

- **판정창은 비트맵이 아니라 `ApplyDefaults` 인자가 정한다** (`HitObject.ApplyDefaultsToSelf` → `HitWindows.SetDifficulty`). 주입을 우리가 하므로 노트별 OD 지정·세션 중 전환이 가능 → 측정 단계만 OD 8.5로 돌리는 경로가 확보됨
- **인게임 판정창 밖 입력은 `JudgementResult`를 만들지 않는다** (`DrawableNote.CheckForResult`가 `HitResult.None`이면 `return`). 즉 "게임은 사용자 OD, 계산기는 8.5 고정" 방식은 사용자 OD가 8.5보다 높을 때 입력이 유실돼 측정이 왜곡됨. 노트별 OD 지정이 정답
- 정한 정확도 공식(분모 320, 분자 `[320,300,200,100,50,0]`)은 **lazer mania 네이티브 판정 등급과 동일 척도**라, OD를 우리가 통제하면 `JudgementResult.Type`을 그대로 매핑하면 됨 — 자체 판정창 구현 불필요, 마디 단위 집계기만 만들면 됨

## 무한 트레이닝 전용 스킨 위젯 2개

측정 알고리즘보다 위젯을 먼저 만드는 순서라, 실질적으로는 **위젯 ↔ 알고리즘 계약을 먼저 확정하는 작업**이 됨.

### 사전 분석

- **런 내부는 검사 불필요** — 런의 컬럼은 연속 정수라 전부 서로 다르고(최대 길이 4 = 컬럼 수), 간격 3 규칙은 거리 2 이내만 문제 삼는다. 실제 제약이 걸리는 곳은 런 시작 지점뿐이며 조건은 `S ∉ {P,Q}`와 `S+d ≠ Q` 둘로 압축된다(세 번째 노트부터는 `Q`와 거리 3이라 자동 안전)
- **데드락 없음** — `{P,Q}` 6쌍을 `Q`값까지 나눠 전수 확인, 어떤 상태에서도 길이 2 이상이 가능한 `(S,d)`가 최소 하나 존재. 마디 재시도 로직이 필요 없음

### 실기 피드백 — `1/2/3`·`4/3/2` 편중 및 연속 반복

**원인 진단**: 직전 두 노트 `(P,Q)` 12가지 상태별로 "길이 2 이상인 런"의 개수를 전수 조사한 결과 **병목 상태 4개**를 발견 — `(1,3) (2,3) (3,2) (4,2)`, 전부 직전 노트가 가운데 컬럼일 때다. 이 상태에서는 다중 노트 런의 **시작점과 방향이 하나로 고정**되어(`(2,3)`→`1→`, `(3,2)`→`4←`) 길이만 다를 뿐 같은 출발이 반복된다. 게다가 `1,2,3`은 끝나면 `(2,3)`이 되어 **자기 자신을 다시 부르는 자기 루프**를 만든다. 나머지 선택지는 전부 길이 1이라 그 구간에서 들리는 유일한 덩어리가 하나뿐인 것도 체감을 키움

**대책 3안 제시** — (A) 병목 상태로 끝나는 런에 가중치 페널티(무상태) / (B) 직전 런과 동일한 서술자 회피 / (C) 간격 2를 마디당 N회 허용(덴시덤프 방식, 병목 자체 제거). 사용자는 **B의 변형**을 선택 — *같은 런이 2연속이면 세 번째는 반드시 다른 런*

**구현**: `Run(Start, Direction, Length)` 서술자를 인스턴스 필드 2개로 기억(마디 경계를 넘어 이어짐 — **생성기가 상태를 갖는 유일한 사례**). 배제는 **재추첨**으로 구현해 기존 추첨 절차(시작→방향→길이)를 그대로 두었다 — 튜닝된 선택 분포를 건드리지 않고 조건부 분포만 정확히 잘린다. 길이는 마디 끝 절단까지 반영한 실제 배치 길이를 기록

**안전성 확인**: 배제해도 후보가 남는지 전수 확인 — 최악인 `(1,3)`·`(4,2)`도 서술자가 2개라 하나를 빼도 1개가 남는다. 배제 대상이 뽑힐 확률은 어떤 상태에서도 1/2 이하라 재추첨 상한 16회면 충분

## sunnySR 계산 분석 (합성 보면 설계용)

- **윈도우별 시계열은 SR에 쓰이지 않는다** — sunny는 osu! 본가 `StrainSkill`(400ms 섹션 피크 + 감쇠)을 상속하지 않고, **노트당 strain 값 하나**만 리스트에 쌓는다. `GetStrainTimeline`/StrainGraph는 거기에 시각을 붙여 리샘플·스무딩한 표시 전용 파생물이며 SR로 되먹임되지 않음
- 최종식: `raw = 0.22×(94.5~91.5 백분위 평균) + 0.188×(84.5~81.5 백분위 평균) + 0.55×(λ=5 멱평균)` → `× W/(W+60)` → 9 초과분 `/1.2` 압축 → `× 0.975`
- **정렬 후 집계하므로 시간 순서가 버려진다.** SR은 "노트별 strain 다중집합 + 노트 수"만의 함수 — 어려운 구간의 위치·분산이 값에 영향을 주지 않음
- **백분위 항은 상위 5.5%(고)·15.5%(중)를 아예 보지 않는다.** 피크를 잡는 건 λ=5 멱평균뿐이고 그마저 전체 노트 수로 희석됨. 상위 5%만 2배로 어렵게 해도 raw는 +12%, 10%면 +42%, 전체면 +100% — **짧고 뾰족한 피크가 강하게 깎이고 고른 난이도가 높게 평가됨**
- 짧은 맵 보정 `W/(W+60)`이 합성 보면에서 지배적. 우리 패턴은 마디당 노트가 32~48로 제각각이라 **마디 수를 고정하면 패턴마다 보정 계수가 달라져 난이도와 무관한 계통 오차**가 생김

## 단기 실력측정 구현

### 확정된 알고리즘

- 지속상승: 통과 시 +1스냅, 미달 시 동결, **연속 2세트 미달**로 이탈. 결과는 기록하지 않음
- 휴식상승: 이탈 세트 bpm − 1스냅에서 시작. 통과 +1스냅 / 미달 −1스냅, **어떤 bpm이 누적 3회 미달**하면 그 bpm − 1스냅으로 확정. **검증 단계는 백지화되어 휴식상승에 흡수됨**
- 상수: 대분류 T1/T2 = 스트림·핸드스트림·덤프 (97,94), 코드잭 (98,95). 세부패턴 (시작bpm, 스냅, 휴식) = 드르륵(100,5,2000) / 싱글핸스(80,5,2000) / 싱글덤프(100,5,2000) / 덴시덤프(100,5,2000) / 24코드잭(110,2,2000)

### 실기 버그 수정 + 코드 리뷰

- **체크박스가 먹통이 되는 버그** — 체크박스에 연결한 `BindableBool`을 `load()` 지역 변수로 둔 게 원인. **`Bindable.BindTo`는 약한 참조**라 GC가 수거하면 연결이 조용히 끊긴다. bpm 스테퍼가 트리거였던 이유는 합성 보면 1000노트 계산이 GC를 유발했기 때문 → 행의 **필드로 승격**
- **위젯에서 현재 행만 sunnySR이 나오던 버그** — 이전/다음/다다음은 `StarRating = 0` 하드코딩이었음. **자리마다 독립 요청**(자리별 CTS + `ConcurrentQueue` 회수)으로 교체. 요청 슬롯이 하나뿐이라 동시 4건을 못 받던 구조도 함께 해결
- **`Update()` 무한 루프 가능성** — `enqueueSet`이 조기 리턴하면 `setsInFlight`가 안 늘어 프레임이 통째로 멎는다. 반환값으로 빠져나가도록 수정 (잠재적 행)
- **`Dispose`에서 `Bindable`을 건드리던 문제** — `Dispose`는 비동기 폐기 스레드에서 돌 수 있어, 구독 위젯이 업데이트 스레드 밖에서 드로어블을 수정하게 된다. `TrainingSessionState.Reset()`을 **`OnExiting`으로 이동**, `Dispose`는 이벤트 해제·취소만
- **세부패턴 전환 시 마디 연속성이 이어지던 문제** — 시퀀서의 `lastGenerated`가 앞 패턴의 마디를 새 생성기에 넘김. `ResetContinuity()` 추가
- 검토 후 문제없음 확인: 세트 노트 수 일치(단노트만 주입, 강제 미스도 판정 발생), `failCounts`의 double 키 정확성, 백그라운드 `Schedule` 스레드 안전성, 휴식 대기 중 시퀀서 시각 밀림 방지
